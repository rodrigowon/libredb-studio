# Create Table — selective upstream checkpoint 2

Source: upstream `2f78fc761b6313fe50127f8221874770fe653e70` (#651).
The fork already had the relevant parent behavior and capability gates; no
prerequisite commit, dependency update or theme changes are needed.

## Implementation

`src/lib/create-table.ts` holds the upstream dialect table, generated-key intent,
default columns and SQL generation. Keeping these pure functions outside React
allows direct tests of defaults and identifier escaping without adding form fields.
`CreateTableModal` consumes the active connection's `DatabaseType` and continues
to call its existing `onTableCreated` callback only after an explicit user action.
Studio's callback still uses `queryExec.executeQuery(sql)`; no execution path,
API, Query Safety, Safe Mode or provider was changed.

| Engine | Default generated key |
| --- | --- |
| PostgreSQL | INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY |
| MySQL | INT AUTO_INCREMENT PRIMARY KEY |
| SQLite / libSQL | INTEGER PRIMARY KEY AUTOINCREMENT |
| SQL Server | INT IDENTITY(1,1) PRIMARY KEY |
| Oracle | NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY |
| DuckDB | INTEGER PRIMARY KEY DEFAULT nextval(...), preceded by CREATE SEQUENCE IF NOT EXISTS |
| Trino | INTEGER NOT NULL; no generated key, PK or UNIQUE option |

The type lists follow upstream, including SQLite's five affinity spellings,
MySQL JSON/CHAR(36), SQL Server DATETIME2/BIT and Oracle VARCHAR2/NUMBER.
Unknown/absent dialects retain the upstream PostgreSQL fallback. Cassandra and
ClickHouse keep their existing `supportsCreateTable: false`; no capability value
was changed and no additional provider is exposed.

## Adaptations to this fork

- Upstream resets all columns on a dialect change. This fork initializes untouched
  defaults for the new engine, but reconciles edited columns instead: names,
  compatible types and flags survive. INT/INTEGER map to the dialect's key type;
  unsupported types move to its first listed type. Unsupported PK/UNIQUE/generated
  key options are cleared. Unchecking PK also removes the generated-key sentinel.
- Literal defaults survive reconciliation; expressions whose portability is unknown
  are cleared on engine changes. During generation defaults remain unchanged SQL
  expressions, not translated or implicitly quoted string values. The existing
  modal has no default-value input; this checkpoint does not add one.
- Identifiers use the existing dialect-aware quoter in addition to the form's
  unchanged lowercase/underscore normalization. DuckDB's sequence name is quoted
  as an identifier and escaped separately inside the nextval string literal.
- Oracle defaults precede inline constraints. This prevents the generator's
  existing default support from using PostgreSQL modifier order there.
- Chrome and validation messages use 23 keys in the existing `DataTools.createTable`
  catalog section (en/pt-BR). Locale resolution, cookie, English fallback and deep
  merge are unchanged. SQL keywords, type names and generated SQL are not translated.
  The empty-preview instruction is UI text, not part of submitted SQL.
- Upstream's provider/comment-only edits and historical live-probe documentation
  were not copied. No live engine measurements from upstream are claimed for this
  environment. Existing provider capability tests pin the unchanged exclusions.

## Scope and tests

Coverage includes the eight default keys, V1 quoting/constraints/defaults,
dialect-leak regressions, connection arrival after mount, compatible-state
preservation, PK deselection, reset after creation, en/pt-BR parity and explicit
submission. SQLite DDL is exercised only in a disposable in-memory unit database.
The new component suite is registered beside the existing one in
`tests/run-components.sh`; the runner has no other changes.

Existing limitations remain: this is not a general schema designer, composite-PK
builder or SQL safety boundary. Types are selected from the form's fixed list;
defaults are SQL expressions and generated statements require normal execution
review. Database visibility remains PostgreSQL/MySQL/SQLite by default.
